# V4-36: the six folders existed on the mail server; Wavium's list was stale

## What was asked

`claude-mail`'s `rules.json` files mail into nine folders. Six of them —
`INBOX/banque`, `INBOX/gaming`, `INBOX/leboncoin`, `INBOX/pub`,
`INBOX/scolaire`, `INBOX/securite` — did not exist as far as Wavium was
concerned, so `sort.py` reported "classés 0" on 25 consecutive runs while the
inbox held 2780 messages. The owner said he had tried to create them in Wavium
and could not. The chef session
(`/home/oxygen/claude-mail/NOTE-chef-reponse.md`) offered two hypotheses: the
creation fails, or the folders exist on IMAP and Wavium does not resynchronise
its list. Deadline: working before 07:15, for the 07:30 brief.

## What was true

Hypothesis 2, plus a creation that really did report a failure.

1. `occ mail:account:sync 1` (no `-f`) changed nothing: still 15 folders. That
   is what made hypothesis 2 look wrong at first. The command skips the mailbox
   sync when the account was synced less than two hours ago
   (`MailboxSync::sync`, the `!$force && getLastMailboxSync() >= now - 7200`
   guard); only `-f` forces it.
2. Creating `INBOX/banque` through the app's own code path answered **"The
   object could not be created because it already exists."** The folders were on
   Orange all along.
3. A raw `LIST` returned **21** mailboxes, all six among them, each
   `\subscribed \unmarked`. `FolderMapper::getFolders()` kept all 21. The
   database held **15**.
4. One forced `MailboxSync::sync($account, $logger, true, $client)` brought the
   database to 21. `occ mail:mailbox:list 1` now shows the six, ids 16 to 21.

Nothing had to be created. The repair was a forced folder resynchronisation.

### Why the list stayed stale

The only thing that forces a mailbox sync in the background is
`SyncJob` (`SyncJob.php:131`, `sync(..., force: true)`). It sets its own
interval at the end of each run from the Mail UI heartbeat: 15 minutes if the
app was opened within the day, otherwise `DEFAULT_SYNC_INTERVAL`, one hour.

- `SyncJob.last_run` = **01:55:00**, and still 01:55:00 at 02:25 — so at 01:55
  it had set itself to the hourly interval, next run due around **02:55**.
- `tungsten`'s `ui-heartbeat` is **01:58:48**: the owner opened Mail *after*
  that run, which is exactly why the run before it had seen a stale heartbeat.

So the six folders would most likely have appeared on their own around 02:55,
an hour after the owner gave up. Nothing was permanently broken — but from where
he stood, a creation that errored and a list that never changed are
indistinguishable from a feature that does not work.

### The creation did report a failure

`data/nextcloud.log` holds exactly two `mail` errors, both
`POST /apps/mail/api/mailboxes` as `tungsten`:

    2026-11-25T01:54:53  OCA\Mail\Exception\ServiceException
      Could not get mailbox status: IMAP error reported by server.
      previous: Horde_Imap_Client_Exception_ServerResponse
      at apps/mail/lib/Controller/MailboxesController.php:307

`MailManager::createMailbox()` does five things in a row: `CREATE` on IMAP,
fetch the ACLs, detect the special use, force a mailbox sync, read the row back.
Something after the `CREATE` threw, so the call was reported as a failure and
the forced sync at the end never ran.

**Unproven, and not guessed at here:** whether those two POSTs created their
folders on IMAP before failing, and which step threw. The logged trace stops at
the controller frame, and the owner may equally have created all six in
Orange's own webmail after giving up. What *is* measured about this server:

- Orange advertises **no** `ACL`, `LIST-EXTENDED`, `LIST-STATUS`,
  `SPECIAL-USE`, `STATUS=SIZE` or `QUOTA`.
- `getACL()` on it raises exactly the logged class and message
  (`Horde_Imap_Client_Exception_ServerResponse: IMAP error reported by
  server.`); `getMyACLRights()` raises `NoSupportExtension`.
- `fetchFolderAcls()` is already guarded by the `ACL` capability and swallows
  Horde exceptions, so it is not the culprit: on an existing folder it succeeds.
- `listMailboxes(..., STATUS_ALL)` and `status(..., STATUS_ALL)` both succeed on
  an existing folder.

Everything testable without writing to the owner's mailbox succeeds. Naming the
failing call needs one probe folder created and then removed on the real
account — a write nobody authorised tonight. Recipe for whoever picks it up:
create `INBOX/wavium-probe` through `MailManager::createMailbox()` with the
Horde frames logged, read which command the server answered `NO`/`BAD` to, then
delete the folder.

The shape of the bug is clear regardless: **on a server without these
extensions, creating a folder reports a failure, and skips the
resynchronisation that would have made the folder visible.**

## Done, on the live instance

- Verified from the agent's side: `mail_accounts` over MCP with the real
  `claude-mail` token returns 21 folders, all six expected names present.
- `sort.py`, plan only: **1243 mails to file** (`leboncoin` 364, `pub` 280,

  absent" warning. It had been 0 for 25 runs.
- The 02:20 cron tick picked it up by itself and drained the backlog:
  `--- 2026-11-25 02:20:03 apply, 1243 prevus` then `classes 1243, echecs 0`.
  The 02:30 tick overlapped it and reported `classes 401, echecs 0` (mostly
  re-moving mail the first run had already filed, which succeeds as a no-op).
  Zero failures in both.
- Measured on the mail server afterwards, by STATUS per folder: `INBOX` 2784 ->
  **1541** messages, exactly the 1243 that were planned; the six folders now
  hold **1532** (leboncoin 487, scolaire 312, pub 303, gaming 236, securite
  102, banque 92). How much of that was already there is not known: their
  initial count of 0 was a stat nothing had ever fetched, and the `\unmarked`
  attribute means "nothing recent", not "empty". So the 1243 that left the
  inbox is the solid number, not the 1532.
- `sort.py` in plan mode now: 1537 scanned, **0 to file**, 1537 untouched
  (human senders and unrecognised domains) -- the backlog is gone.

### Where the filed mail shows up

Measured during the run: `INBOX`'s local rows fell from 2784 to 2237 while the
six destination folders still read 0. That is expected, not a loss. The move
happens on the mail server, and `ImapToDbSynchronizer::syncAccount()` skips any
mailbox that is not Inbox, Trash, Sent, Snooze or special-use `All` unless its
`sync_in_background` flag is set -- and on this account **no** folder has it
set, including the three that have always worked. They filled their local rows
the normal way: the first time each was opened, on demand. `comandes-ventes`
holds 377 local rows with the flag off, which is the proof.

So the newly filed mail is on Orange now and appears in Wavium as each folder
is first opened. Nothing was changed about that: turning the flag on for six
folders would be an unrequested behaviour change, and it is the folder menu's
own setting if the owner wants it.

Nothing else on production was written: no mail deleted, no tag changed, no
token touched; `sort.py`, `brief.sh` and `rules.json` untouched; no change to
`.env`, the crontab, or any schema. The diagnostic scripts ran from the
container's `/tmp` and the repository is unchanged except for this report.
