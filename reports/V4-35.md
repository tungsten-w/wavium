### The agent's tags work

`mail_message_tag` is live (24 tools in `tools/list`). Tested with the real
`claude-mail` token, on one mail, through Caddy:

- `add: ["important"]` on `1:c24dad9b5eb9907cfcbfcf661cc7002c` ("Petit rappel
  concernant votre garantie des dépôts", message id 3547) answered
  `{"tags":["important"]}`.
- In the database: one `oc_mail_triage` row, `version=agent`,
  `model=tagged-by-agent`, `needs_action=1`, everything else null.
- Read back through `mail_message_list`: `tags: ['important']`.
- `remove: ["important"]` answered `{"tags":[]}`.
- The row it left behind (all predicates 0, no category) was deleted:
  `oc_mail_triage` is back to 0 rows, as before the test. No other mail touched.

No AI is involved in any of that: the agent's answer *is* the classification
(`server/agent/mail/write.ts`), and the table takes a partial row, so a mail
nobody classified can still be tagged. The UI reads the same row whoever wrote
it (`TriageService::forMessages`, no filter on `model`), and the hash both
sides use is the same (`msgHash` in `server/agent/mail/keys.ts` ==
`TriageService::hash`).

### The colors

**The 5 agent tags** become chips through `TriageChips`
(`apps/mail/web/index.tsx`), one CSS class per word. `urgent`, `important`
(class `act`) and `etudes` had a color. `spam` and `promo` (the classifier's
`ads`) had none: they fell through to the neutral `.ml-tag`, the same grey as
"Newsletter" or "Other". Two of the five words claude-mail is about to use were
not distinguishable. Fixed in `apps/mail/web/style.css`.

**Mail's own IMAP tags** keep their color in `oc_mail_tags.color`, and that
column defaults to `'#fff'`. `IMAPMessage::getTags()` builds a tag from a
keyword the server reports without setting a color, and
`TagMapper::tagMessage()` inserted it as it came. So every tag Mail
discovered by itself was white, and
`.ml-utag` draws the text in `var(--tag)` over 14% of the same color: a white
chip on a white background. On this instance:

    id | display_name     | color   | mails
     7 | Promotion        | #fff    |   668
     1 | Important        | #FF7A66 |     3
     8 | Loadremoteimages | #fff    |     3
     6 | Forwarded        | #fff    |     2

668 of the 676 tagged mails — 99% — carried a tag the owner could not see.
Fixed twice over: `TagMapper::tagMessage()` now gives a discovered tag a color,
and the UI reads white as "nobody chose one" rather than as a choice, so the
rows already in the database become visible without touching them.

### Self-hosted: the headers yes, the text no

| | Mails |
| --- | --- |
| On the mail server (IMAP `STATUS`, per folder) | 3740 |
| Metadata in Wavium (`oc_mail_messages`) | 3547 |
| Full text in Wavium (`oc_mail_bodies`) | 796 |

So **22% of the mail is readable without Orange**. The rest is a subject, a
sender and a preview; the body still lives only on the server. Seven folders
have no local copy at all (`INBOX/DRAFT` 48 mails, `igmm` 28, `logement` 5,
`CROUS` 4, `factures importantes` 3, `admin important` 3, `CARMF` 1 — 92 in
all). `INBOX/QUARANTAINE` is the one folder kept whole, 48 of 48.

What fills that table is `TriageService::storeBody()`, and it is called from
exactly two places: when classification fetches a mail, and when a mail is
opened. The agent's `mail_message_get` counts as opening one
(`server/agent/mail/read.ts`, the `fetchBody` fallback). Classification fetches
the body *before* it calls the AI (`buildInput`, then `askAi`), and the run
stops at the first 409, so with no AI provider the pipeline still archives one
mail per 10-minute window and nothing else. Reading mail is what archives it.

Not changed: this is how the design works, not a bug. It is written here
because "are the mails really self-hosted" has a number, and the number is 22%.

### `make test` was broken, by the build

`deploy/build.sh` extracts the tree into `deploy/src` as the Docker build
context and left it there — 478 MB, a second copy of the repo inside the repo.
`make test-server` is `bun test server/`, and that filter matches *any* path
containing `server/`, so every server test ran twice, the second time from
`deploy/src/server/` — a tree whose `deploy/` the same script had just deleted.
V4-34's compose-stack test failed on both production stacks for that reason
alone. The image built yesterday evening is what put the snapshot there, so
`make test` has been red since, on a green tree.

`build.sh` now removes the snapshot in its EXIT trap.
