# P2-7: OAuth 2.1 for MCP (discovery, PKCE, consent screen)

- Branch: `night/P2-7` · Instance: session B (main session, Claude) · Date: 2026-11-13
- Status: done

## Done

An MCP client (Claude, Cursor, an MCP inspector...) can now connect to
Atrium with a browser login and a consent screen instead of a token copied by
hand. It follows the MCP authorization spec 2025-11-25 (read for this task:
modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

- `server/agent/oauth.ts` (Bun, no PHP):
  - discovery: `/.well-known/oauth-protected-resource[/agent/mcp]` (RFC 9728)
    and `/.well-known/oauth-authorization-server` (RFC 8414,
    `code_challenge_methods_supported: [S256]`,
    `client_id_metadata_document_supported: true`); a 401 at `/agent/mcp`
    carries `WWW-Authenticate: Bearer resource_metadata="…"`;
  - clients: Client ID Metadata Documents (https `client_id` URL, fetched
    through the P1-5 SSRF guard, 5 s, 64 KB, `client_id` must match, cached
    1 h) and Dynamic Client Registration (RFC 7591); public clients only;
    redirect URIs must be https, http on a loopback host (any port, RFC 8252)
    or an app scheme (cursor://…);
  - `/agent/oauth/authorize`: PKCE S256 required, `resource` (RFC 8707) must
    be this MCP endpoint; a bad client or redirect URI gets an error page and
    never a redirect; later errors go back to the app with `state` and `iss`;
  - consent bound to the first user who opens it, answered once, 15 min;
  - `/agent/oauth/token`: one-time code (10 min; a replayed code revokes what
    it gave), PKCE check, client and redirect check; Atrium's own opaque
    tokens stored hashed: access 1 h, only accepted at `/agent/mcp`, refresh
    30 days rotated at each use, a replayed refresh token revokes the grant;
  - `/agent/oauth/revoke` (RFC 7009).
- The token acts as the agent the user picked: same grants, approvals, pause
  and journal as an agent token. Deleting the agent ends its grants.
- Owner API: `GET /agent/v1/owner/oauth/flows/<id>`, `POST …/approve
  {agent}` (own agents only), `POST …/deny`; `connectedApps` on each agent;
  `DELETE /agent/v1/owner/agents/<uid>/oauth/<grant>`; `POST agents` with
  `token: false` (an agent made for OAuth gets no plain token).
- UI: Settings > Connect an agent (`/settings/user/agent-connect`, not in the
  menu): the app's name, where the browser goes back (host in bold), a
  warning for local addresses, the app's metadata URL for CIMD clients, "Act
  as" one of your agents with what it may do, or a new agent (name + preset);
  Allow / Deny. Settings > Agents lists "Connected apps" per agent with
  Disconnect.
- `server/index.ts` sends `/.well-known/oauth-*` to the agent layer (CardDAV,
  CalDAV and the other well-known URLs are unchanged: checked).

Why not Nextcloud's `oauth2` app: its clients are registered by an admin and
its tokens act as the whole user account; MCP clients register themselves
and here must act as one agent only. The app is untouched (ADR 0008).
