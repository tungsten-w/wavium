# P1-2: Chunked uploads without the whole body in RAM

- Branch: `night/P1-2` (on top of `night/P1-3`) · Instance: main (tmux session "main") · Date: 2026-11-12
- Status: done

## Done

Before: a request without `Content-Length` (`Transfer-Encoding: chunked`: WebDAV
clients like davfs2, Finder, some sync tools) was read with
`await req.arrayBuffer()` in `server/php.ts`: the whole upload in RAM, so a
multi-GB PUT could kill the container (the host has 8 GB).

- `server/spool.ts` (new): `spoolBody()` reads a chunked body; up to 1 MiB it
  stays in memory, past that it goes to a private temp file
  (`mkdtemp` + mode 0600) and PHP is fed from the file. It enforces
  `maxBytes` (→ 413), and removes the temp file when the client breaks off or
  the body is too big.
- `server/php.ts`: uses it; the temp dir is removed once PHP has the whole
  body, or once PHP answered (it may answer without reading the body; on
  Linux the open file stays readable, tested).
- `PhpTarget.maxBody` (from `ATRIUM_MAX_BODY`, P1-3) caps the spool too.
- **Bug found by the 2.5 GB test and fixed**: once a big chunked body is
  spooled, replaying it to PHP takes many seconds while the client sends
  nothing, so the idle timeout (P1-3) closed the connection (ECONNRESET).
  `servePhp`'s `onBodySent` now fires as soon as the client's body is fully
  in (after spooling), not only after PHP got it.
- `ATRIUM_UPLOAD_TMP` (new, `.env.example`, `compose.yaml`): where to spool.
  Must be on disk, not a tmpfs (on the dev host the `/tmp` is a tmpfs; in the
  containers `/tmp` is on disk, so the default is fine there).
- Test helper `server/testing/fake-fpm.ts` (moved out of `fastcgi.test.ts`,
  new `headersFirst` mode).

Requests with `Content-Length` were already streamed (unchanged).
