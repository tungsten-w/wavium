# V4-27: an `etudes` category, and the labels that could never appear

- Branch: `night/V4-27` (on top of `night/V4-25`) · Instance: Claude (interactive session) · Date: 2026-11-23
- Status: done

## Done

The classifier had no category for school or university: `questions.json` folded
them into `admin` ("university or school, government, taxes…"), so a timetable,
an exam result and a tax notice all came out as the same thing. Meanwhile the
Mail UI still carried four labels — `school`, `finance`, `calendar`, `unknown` —
that no mail could ever have, because they were not in the classifier's choice
list. A `School` chip existed and could never match anything.

- `apps/mail/lib/Service/Triage/questions.json`: new `etudes` choice, placed
  after `work` ("School, university or training: courses, timetables, enrolment,
  exams, marks, coursework, internships for a course, student services, teachers
  and school admin"). `admin` no longer mentions school or university, so the two
  do not compete for the same mail. Question set bumped to `mail-v3`.
- `server/agent/mail/read.ts`: `etudes` added to `CATEGORIES`, so
  `mail_message_list` accepts `category: "etudes"` and the rules engine and the
  correction route (both import this list) accept it too.
- `apps/mail/web/api.ts`: `etudes: 'Studies'` added to `categoryLabels` and
  `etudes` to `filterCategories`; `school`, `finance`, `calendar` and `unknown`
  removed from `categoryLabels`, and the dead `unknown` removed from
  `urgencyLabels`. The Studies chip, the Curated picker and the "Where your mail
  goes" chart all follow from those two lists, so they needed no change.
- `apps/mail/web/style.css`: `.ml-tag--school` became `.ml-tag--etudes` (the
  class is built from the category name, so the old one was unreachable).

Bumping the version is free: `TriageService::enqueue()` works off a
`scannedUpTo` cursor and the queue table, never off the version, and
`mail_triage` is unique on `(account_id, msg_hash)`. No mail is reclassified and
no euro is spent. The flip side, worth knowing: mail already classified keeps
its `mail-v2` answer and will never come out as `etudes` until something
re-queues it — that is V4-28's job, not this one.

## Tested

Two new tests, one per side, because the three lists had drifted silently once
and nothing noticed:

- `server/agent/mail/categories.test.ts` (new, 4 tests): `CATEGORIES` is exactly
  the choices in `questions.json`; every choice has a real description; `etudes`
  exists and `admin` no longer mentions school or university; the set is
  `mail-v3`.
- `apps/mail/web/categories.test.ts` (new, 4 tests): `filterCategories` is
  exactly those same choices; `categoryLabels` has one label per category and no
  label without a category; `etudes` reads as "Studies"; `urgencyLabels` matches
  the question's levels the same way.

Checked the tests really test: with `etudes` taken back out of `CATEGORIES`,
2 of the 4 server tests fail (`CATEGORIES is exactly what the classifier can
answer`, `etudes exists and admin no longer swallows…`); restored, they pass.

Two existing tests asserted the old set and were updated:

- `server/ai/triage.test.ts` — the forced-tool enum and the version.
- `apps/mail/tests/Unit/Atrium/TriageAiBackendTest.php` — now asserts that the
  version PHP forwards is the one `questions.json` carries (and that it is
  `mail-v3`), instead of a bare literal. Renamed accordingly.

## Questions for the human

- Should `etudes` be hidden by Curated? It is not, today: `DEFAULT_CURATED_HIDES`
  stays `ads, spam, newsletter, social`. Course and timetable mail is noisy but
  it is the kind of noise you probably want to see.
- The category value is `etudes` (no accent, matching the `[a-z][a-z0-9_]*`
  shape the question names use) and it reads as "Studies" in the UI, which is in
  English like the rest. Tell me if you would rather the UI said "Études".
