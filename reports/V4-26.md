# V4-26: classification turns itself on when an AI provider is added

- Branch: `night/V4-26` (on top of `night/V4-27`) · Instance: Claude (interactive session) · Date: 2026-11-23
- Status: done

## Done

`triage_enabled` defaulted to false and the only thing that ever wrote it was
the switch on the Mail status page, shown to admins only
(`canManage = groups->isAdmin`). So a freshly configured instance classified
nothing, and everything built on the classification stayed dead with it:
Curated, the category chips, "Needs action", "Why is this mail here?", and the
filing rules — which only ever run on rows added to `mail_triage`. Nobody else
could even see that this was the reason: a non-admin got no line about
classification at all. `TASKS.md` claimed under V4-17 that classification
"starts as soon as an AI is added"; no code did that.

Adding an **instance** AI provider is now the moment the answer becomes yes.

- `TriageService::enableOnFirstProvider()` (new): turns classification on and
  sets the state to `idle`, returning `{enabled, changed, reason}`. It never
  overrides a person — see below.
- `triage_choice_made` (new app config): `setEnabled()`, the only thing a human
  can reach, now records that a human decided. Without it, "off" and "nobody has
  been asked yet" are the same value, and auto-enable would undo a deliberate
  no. `enableOnFirstProvider()` returns early when the flag is set, in either
  direction. It is exposed as `settings.choiceMade` in the status payload.
- `AtriumAgentController::triageAutoEnable()` and
  `POST /apps/mail/api/atrium-agent/triage-auto-enable` (new): internal-only,
  like the rest of that controller (`X-Atrium-Internal` through `guard()`).
- `server/agent/ai.ts`: the `POST /agent/v1/ai/providers` route calls it after a
  successful create, but only when the new provider is `scope: 'instance'` and
  enabled. A personal provider must not flip it — `triage_enabled` is
  instance-wide, so one user's key would start classifying everybody's mail.
  The call is never fatal: if Mail does not answer, the provider is still saved
  and the error is logged.
- `apps/mail/web/Status.tsx`: `ClassificationLine` (new, exported for the test)
  tells a non-admin what is happening — "Classification is on", or off with the
  reason: no provider yet ("An admin adds one in Settings > AI") versus a
  provider exists but the switch is off ("An admin can turn it on from this
  page"). Admins still get the switch, unchanged.

The switch stays admin-only on purpose: it spends the instance's AI budget.

End to end on the dev stack, which is the part that matters:

1. before: `settings.enabled false`, `choiceMade false`, `state disabled`;
2. `POST /agent/v1/ai/providers {"scope":"instance","kind":"mock"}` as admin →
   `settings.enabled true`, `state idle`, `choiceMade` still false;
3. admin turns it off (`PUT /apps/mail/api/triage/enabled {"enabled":false}`) →
   `enabled false`, `choiceMade true`;
4. a further instance provider → still `enabled false`. The no held.
