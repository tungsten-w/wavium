## Done

### Fixed: picking a colour, then a wallpaper, answered 500

Found in the log of a real install (`POST /apps/theming/background/default`,
`TypeConflictException`), then reproduced and fixed.

Atrium's own `BeforePreferenceListener::bumpCacheBuster()` writes
`theming/userCacheBuster` with `setValueString` when the accent colour changes
-- that is how a new accent reaches classic pages. Nextcloud stores the *type*
of a value with it and refuses to change it afterwards, and the upstream
`UserThemeController::setBackground()` wrote the same key through
`IConfig::setUserValue`, i.e. type "mixed". So: pick an accent colour in
Settings > Appearance, then pick any wallpaper -> 500, every time, for good.

Both writers now say string (`apps/theming/lib/Controller/UserThemeController.php`).
Rows already written either way become valid again, because a value stored as
"mixed" accepts any type on the next write -- no migration needed. The same
trap sat in `RestoreBackgroundImageColor` for `primary_color`, which
`RandomAccentListener` writes as a string; fixed the same way.

Tests: `tests/lib/Theming/UserThemeCacheBusterTest.php` (the controller writes
that key with the typed setter and never with the legacy one; checked by
reverting the fix, both tests fail), and an end-to-end test that does exactly
what the person did -- accent colour, then three kinds of wallpaper, then the
colour again -- and fails on any 4xx/5xx from `/theming/`.

### Fixed: Notes dropped letters while you typed

The worst of the night, and it only showed up once a test *used* the app
instead of opening it: typing `SONDE 1795...` into a note saved `SNE
7540301799`. An earlier run had saved "Courses du ..." as "Couses du ...".

`LiveEditor` keeps CodeMirror in sync with the React value it is given:

```tsx
useEffect(() => {
    if (v && props.value !== v.state.doc.toString()) v.dispatch({ ...insert: props.value })
}, [props.value])
```

Every keystroke travels editor -> `onChange` -> parent state -> back into this
effect. Any letter typed during that round-trip is already in the document but
not yet in `props.value`, the two differ, and the effect replaces the whole
document with the older text -- deleting what was typed in between. The faster
you type, the more you lose.

The sync now does nothing while the editor has the focus: an outside change
(the other side of a conflict, a reload) only ever matters when the editor is
not the thing being typed into. Proven by `doing.spec.ts`, which types a
sentence, comes back to the list cold and asserts the text letter for letter --
it failed before the change and passes after.

### Fixed: changing the accent colour answered 500 on a new account

The same trap, one layer up, and found by the end-to-end test written for the
one above. Atrium gives every new account a random accent
(`RandomAccentListener`, on `UserCreatedEvent`) and wrote it with
`setValueString`. Settings > Appearance changes the colour through the
preferences API, which writes values untyped ("mixed"). So the **first** colour
change a person ever made answered 500 and did nothing.

The accent is now written through the legacy setter, untyped, exactly like the
preferences API writes it. For accounts that already carry a typed one,
`BeforePreferenceListener` drops the stored value just before the new colour is
written (`dropTypedAccent()`), so they repair themselves at the first change --
no migration, and nothing to run by hand.

Tests: `tests/lib/Theming/AccentColourTypeTest.php` (four cases: a new account
gets an untyped accent, a typed one is dropped, an untyped one is left alone
and still bumps the cache buster, an invalid colour changes nothing; the repair
case fails if the call is removed). In the browser, the Appearance test above
now passes for an account whose accent was stored typed (bob) -- it failed
before the fix.

### Fixed: a fresh install logged an error on every classic page

`core/js/mimetypelist.js` is generated (`occ maintenance:mimetype:update-js`)
and therefore gitignored, so `deploy/build.sh`, which exports the *committed*
tree, shipped an image without it. Every classic page then logged "Could not
find resource core/js/mimetypelist.js to load" until an admin ran that command
by hand. The dev stack never showed it: `deploy/dev/init.sh` copies the file
from the release. `deploy/Dockerfile` now does the same, next to the other
parts the release adds that the repository does not carry.

### Fixed: a mail account created by command had no tags

Found in the dev instance's log: twelve "Could not find important tag for
alice" errors from `ImapToDbSynchronizer`. `oc_mail_tags` was empty.

Adding an account in the interface goes through `SetupService`, which calls
`TagMapper::createDefaultTags()`; `occ mail:account:create-imap` -- the path
the seeder and any script uses -- did not. The consequence is not only log
noise: the synchroniser skips the important-mail classification when that tag
is missing (`if ($importantTag)`), so new mail on such an account was never
flagged important. The command now creates the tags, like the interface does.

Verified by hand: creating an account with the command now writes the five
default tags (`$label1`..`$label5`); before the change the table stayed empty.
Accounts created earlier are repaired with the command upstream ships for it,
`occ mail:account:add-missing-tags`. The production install is not affected --
it has no mail account yet, and the interface path was always correct.

### Fixed: the browser tab died during the browser tests

`make test-e2e` ran Chromium with the container default of 64 MB for
`/dev/shm`; past that the renderer dies and Playwright reports "Page crashed",
which it did on the Mail app at phone width. `--ipc=host` (Playwright's own
recommendation) fixes it. The same target now also passes `E2E_GREP` through,
so one test can be run alone.

### Fixed: the Messages browser test skipped the flow it was meant to test

It asked `isVisible()` for the "Show the QR code" button straight after
`goto()`. That call does not wait, so on a slow machine it answered "no" while
the app module was still mounting: the pairing step was skipped, and the test
then waited ninety seconds for conversations that only pairing creates, until
the tab died ("Target crashed"). It now waits for the page to be in one state
or the other before asking which. 17 seconds instead of a 90-second crash.

Measured before fixing, to be sure it was not the app: the Messages page left
open sits at a flat 10 MB heap and 172 nodes, and it does show the QR button --
the test was reading it too early.

### Added: tests that use the apps instead of opening them

Every browser test so far opened pages. `tests/e2e/doing.spec.ts` does what a
person does on the first day and checks it survives a reload: write a note
(letter for letter), add a task, tick it, find it under Completed, put a file
in Files. The note case is what caught the editor bug above; the task case had
to be written against what the app really does (ticking takes the task out of
the open list, so `check()` cannot read the box back -- click, then look under
Completed).

### Added: the screens a newcomer actually sees

Every e2e test logged in as alice or bob, who have demo mail, events and
contacts, so no test ever opened the first screens: empty states, "connect
your mail", "no AI provider yet". The demo instance now also has an account
with nothing in it (`EMPTY_USER` in `deploy/dev/seed.php`, chloe), and
`tests/e2e/newcomer.spec.ts` walks every app with it on desktop and at phone
width and checks that each page arrives, that nothing is left spinning, that
nothing scrolls sideways on a phone, that no request fails and that the two
dead ends a new person can land in (Mail with no account, Settings > AI with
no provider) offer the way out. Screenshots land in
`tests/e2e/results/screenshots/new-<app>.png`.

That walk runs one short-lived tab per app instead of twenty-odd navigations
in the same one: it is what a person does, and it keeps the browser's memory
flat on a small machine.

  classic pages and the Dashboard widgets follow the account language, so a
  French account reads "Good night, Chloé" above "Fichiers recommandés",
  "E-mails importants", "il y a 6 minutes". It is the most visible rough edge
  for a newcomer, and it is a translation project (every string of the React
  UI through a t() helper, then a French catalogue), not a fix -- worth its own
  task.
- **Mail's first screen asks for IMAP and SMTP servers, ports and encryption**
  right away. The providers are filled in once an address is typed, but what a
  newcomer meets first is a server form. Asking for the address and the
  password first, and folding the rest away unless the provider is unknown,
  would be kinder. Needs a design decision, so not done tonight.
- Chromium logs `Unrecognized feature: 'bluetooth'` for the `Permissions-Policy`
  header on every page. Harmless (an unknown feature is ignored) and only in
  devtools; dropping it would only remove a deny in browsers that do support
  it, so it is left as is.
- Not a Wavium problem, but it shaped the night: the machine was out of memory
  (swap 2.0 Gi of 2.0 Gi used) with the production stack and the dev stack both
  up, which is what killed the browser the first time.
