# P1-3: Bun limits (`idleTimeout`, `ATRIUM_MAX_BODY`)

- Branch: `night/P1-3` · Instance: main (tmux session "main") · Date: 2026-11-12
- Status: done

## Done

Before: `Bun.serve({ maxRequestBodySize: Number.MAX_SAFE_INTEGER, idleTimeout: 0 })`,
so any client could hold a connection open forever and send a body of any size.

- `server/limits.ts` (new): reads the limits from the environment, refuses bad
  values with a clear message at start-up.
  - `ATRIUM_MAX_BODY`: PHP syntax (`10G`, `512M`, bytes, `0` = no limit).
    Default = `PHP_UPLOAD_LIMIT`, else `10G`, so Bun never refuses what PHP
    accepts (prod sets `PHP_UPLOAD_LIMIT=10G`). Bigger bodies get **413** from
    Bun, before PHP sees them. Bun counts chunked bodies too.
  - `ATRIUM_IDLE_TIMEOUT`: 1..255 s (Bun's max), default **60**.
  - `ATRIUM_PHP_TIMEOUT`: 0..255 s, default **0**.
- The idle cut only protects the phase where **the client** is sending. Bun's
  idle timer also runs while the handler awaits PHP, so a slow PHP page (DAV
  MOVE that assembles a big chunked upload, a zip download being built) would
  have been cut after 60 s. So once the body is fully received the request's
  timeout is switched to `ATRIUM_PHP_TIMEOUT` (`server.timeout(req, n)`; 0 = off,
  PHP-FPM's `request_terminate_timeout = 3600` bounds it):
  - PHP routes: `fastcgi()` got an `onBodySent` callback, fired after the last
    STDIN record; `servePhp()` passes it through (`opts.onBodySent`).
  - `/agent/*`: the (small JSON) body is read first, then the timeout is lifted,
    so a slow tool call (IMAP) is not cut.
  - Static files and the shell page: unchanged (data flows, nothing to wait for).
- The start-up log line prints the limits.
- `compose.yaml` and `.env.example`: `ATRIUM_IDLE_TIMEOUT`, `ATRIUM_PHP_TIMEOUT`
  added, `ATRIUM_MAX_BODY` documented.
