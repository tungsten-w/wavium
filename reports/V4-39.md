## The one decision that shaped everything: who calls whom

`claude-mail` is not Wavium. It is a Claude Code agent running on the machine
that hosts the instance, on the owner's personal subscription, started by cron.
A chat window needs the two sides to meet, and there were three ways:

1. **Wavium calls it.** Real streaming, and an answer that feels immediate. It
   needs a listener on the host, a shared secret inside a container, and
   `extra_hosts` in the compose file — the app containers are on `backend`
   (`internal: true`) and have no route to the host today, so this would open
   one. Measured, not assumed: `getent hosts host.docker.internal` fails in the
   live container.
2. **Run the agent in a container.** Then `~/.claude` — a personal
   subscription's credentials — would have to be copied into it.
3. **The agent calls Wavium.** It already holds a token and already reaches the
   instance. Nothing new is exposed.

**Chosen: 3.** The cost is honest and small: no push, so the answer arrives
when the agent next checks in. A real run takes tens of seconds anyway, so the
10-second poll is not what the owner waits for. Written up as ADR 0011.

## Done

**The thread** (`oc_atrium_agent_chat`, agent-layer migration 5): one per
agent, both directions. `taken_at` is when the agent picked a message up, which
is what makes a message answered exactly once.

**The owner's side** (`server/agent/chat`, session cookie):
`GET /agent/v1/chat` lists the agents they can talk to and what is waiting;
`GET /agent/v1/chat/<uid>` reads the thread (`?after=` for polling);
`POST` sends. The built-in assistant is left out of the list: it has its own
panel and its own provider, and it is not somebody to write to.

**The agent's side**, the same two operations in two shapes:

- tools `chat_poll` and `chat_say`, for an agent that speaks MCP;
- `GET /agent/v1/chat/-/pending` and `POST /agent/v1/chat/-/say`, plain text,
  for an agent whose runner is a shell script.

Both tools are **base tools** (`area: null`), so no new grant area was added. A
message the owner deliberately typed to their own agent is not access to their
data, and the answer is the agent's own words; nothing in this module touches
mail, files or calendar, so there is nothing to grant. A paused agent is
refused on all four paths — `callTool` already does it, and the plain-text
routes check the same thing.

The plain-text pair is a deliberate second shape, not duplication: the first
runner I wrote used `python3` for JSON, which is absent from the test container
and is exactly the kind of dependency that makes such scripts rot. With plain
text the runner needs nothing but `curl`.

**The panel** (`core/web/shell/`): a "Talking to" picker in the assistant
header — `Assistant`, then each agent with its waiting count. Picking an agent
swaps the stream for `AgentChat.tsx`, which polls every 4 s and says where the
message actually is: *waiting to be picked up*, *picked up and being worked
on*, or *paused, so it will not read this*. No fake "typing…". With no agent to
talk to, the picker is not rendered and the panel is exactly what it was.

**Settings > AI**, which is where the owner asked for the choice: a card "Your
own agents", one row each, with a `Talk to <name>` button that opens the panel
on it. It sits next to the providers for a reason worth saying out loud: this
agent brings its own AI, so it works on an instance with no provider configured
at all — which is this instance today.

**The runner** (`services/agentchat/chat-loop.sh`, with a README): polls, and
only starts a real run when something is waiting. It keeps the Claude session
id so a conversation continues, drops it after a failure so one bad turn does
not poison the next, takes a lock so two copies cannot both answer, reads the
token from a file per call so it never lands on a command line, and **tells the
owner in the thread when a run fails, times out or says nothing** — the lesson
of the brief that died silently under cron (V4-25).

### End to end on the dev stack

Unit tests cannot prove the wiring (module registered, migration applied, both
auth paths). So, against `make up` with a real agent and a real token:

1. `POST /agent/v1/owner/agents` created an agent for alice with a token.
2. `GET /agent/v1/chat` as alice listed it.
3. `POST /agent/v1/chat/<uid>` as alice: `{"id":1,"from":"you","taken":false}`.
4. `GET /agent/v1/chat/-/pending` with the token returned the message as text.
5. The same call again returned **empty** — picked up once.
6. `POST /agent/v1/chat/-/say` with a `text/plain` body returned `201`.
7. `GET /agent/v1/chat/<uid>` as alice showed both, the first now `taken: true`.

Then **the real runner** against the same stack, with a fake `claude`: it
picked the message up, handed the agent the owner's words with the framing,
ran with `--session-id <uuid> --agent ...`, and posted the answer, which
appeared in alice's thread. Log: `picked up 1 line(s)` / `answered (41 chars)`.
The test agent was deleted afterwards.

This is also what caught a real defect: the dev stack refused to start with
`File not found "core/web/shell/agentChat.tsx"`, because I had named a module
`agentChat.ts` next to a component `AgentChat.tsx` — two files differing only
in case, which is ambiguous for tooling and outright broken on a
case-insensitive filesystem. Renamed to `chatModel.ts`, which is the
convention the shell already uses (`assistantModel.ts`, `aiModel.ts`).
