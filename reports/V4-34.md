# V4-34: classification could never reach the AI, in either production stack

- Branch: `night/V4-34` · Instance: claude-opus-5 · Date: 2026-11-24
- Status: done, and applied to the live instance (verified). What remains is
  not this task: the instance has no AI provider, which is a spending decision.

## Done

The live instance had **3401 mails waiting to be classified and 0 classified**.
The queue's `last_error` said:

    AI unreachable: cURL error 7: Failed to connect to 127.0.0.1 port 80
    for http://127.0.0.1/agent/v1/internal/ai/triage

`ATRIUM_SERVER_URL` is how Mail's `TriageService` reaches the Bun server's
internal AI route. Both production stacks had it wrong, in two different ways,
and both failed silently: the Mail status page kept showing classification as
on while the queue only grew.

- `deploy/wavium/compose.yaml` set `http://127.0.0.1:80` in the `x-app`
  environment block. That block is shared with the `cron` service — and the
  triage worker runs there, where nothing listens on port 80. Measured from
  inside the containers: `app:80/status.php` → 200 from both, `127.0.0.1:80`
  → 000 from `cron`.
- `deploy/compose.yaml` declared no `ATRIUM_SERVER_URL` at all, so PHP fell
  back to its default `http://web:8080` — a service that stack does not have
  (it has `app`, `cron`, `db`, `redis`). That one fails on name resolution.

Both now say `http://app:80`. One value is right for every container of a
stack: from the `app` container the service name resolves to itself (verified,
200), and from `cron` it reaches `app` over the compose network.

New test `server/ai/triage-stack.test.ts` holds the invariant for all three
stacks (dev, `deploy/`, `deploy/wavium/`): `ATRIUM_SERVER_URL` must be
declared, must not be a loopback address, and must name a service declared
under `services:` in that same file.

**This was not caused by the 2026-11-24 disk incident.** The `pre-v42` backup
of 2026-11-23 14:51 already held 3398 queued rows and 0 classified, and 0 AI
providers. Classification had never run in production.

  (`3 pass, 2 fail`); restored, `5 pass, 0 fail`.

  cron` in `deploy/wavium`. Compose recreated `app` too, since the changed
  environment block is shared -- a few seconds of interruption. Both
  containers now report `ATRIUM_SERVER_URL=http://app:80`, and the instance
  came back at its usual times (`/status.php` 200 in 20 ms, `/login` 200 in
  76-124 ms, against 74-105 ms recorded before).
- Proof that the fix took effect, from the live instance: the pipeline was in
  `backoff` until 21:15 after 11 transient failures, so the first tick after
  the change did nothing (correct). At 21:15:17 UTC, one `cron.php` tick moved
  `triage_state` from `backoff` to **`not_configured`**, and `lastError` from
  the cURL 7 message to "No AI for mail triage: no AI provider is configured.
  Add one in Settings > AI." The network-level failure is gone; what answers
  now is the missing provider. The queue is untouched at 3401 `pending`, 0
  parked, 0 attempts counted -- which is what the 409 path is meant to do.
- A first `make test` run failed in `test-php` with
  `failed to set up container networking: network ... not found` — a stale dev
  network left by the `docker compose run` containers of `make lint`, not a
  code failure. `docker compose down --remove-orphans` then `make test` → rc=0.
