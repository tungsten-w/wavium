# Audit Wavium — 2026-11-23

Audit d'usage réel de la branche `release/v4` (`f557cdae`), mené en lecture seule
sur le code et sur une instance de démo neuve (stack dev, `atrium-dev`,
http://localhost:8092). L'instance personnelle du propriétaire (projet compose
`wavium`, `deploy/wavium/compose.yaml`, up depuis 8 h) n'a pas été touchée.

## 1. Synthèse

1. Wavium est déjà une application utilisable : 10 UIs React livrées, le shell,
   le login, les Réglages et la compatibilité clients Nextcloud (OCS 200, DAV 207)
   répondent sur une instance neuve.
2. La suite de tests est entièrement verte : 730 tests Bun, 228 vitest, 130 + 82
   PHPUnit, Daily Todo, `make lint` propre.
3. Mail est l'app la plus avancée (dossiers, lecture, envoi, favoris, snooze,
   tags manuels, « Pourquoi ce mail est ici ? »).
4. **La classification IA est éteinte par défaut** (`enabled: false` constaté sur
   l'instance neuve) : tant qu'on ne bascule pas l'interrupteur, Curated, les
   chips de catégorie, « Needs action » et le moteur de règles sont inertes.
5. **Un agent ne peut poser aucun tag ni aucune catégorie.** Les outils MCP mail
   sont en lecture, plus `seen`/`starred`/`folder`. C'est le manque qui motive
   la fiche n°1.
6. Deux systèmes d'étiquettes coexistent sans pont : la `category` IA (interne
   à Wavium) et les tags Mail (mots-clés IMAP, visibles sur le téléphone).
7. Il n'existe pas de catégorie `etudes` dans le classifieur, alors que l'UI
   garde un libellé `school` mort.
8. Le classement quotidien réel est fait **hors de Wavium**, par
   `/home/oxygen/claude-mail/sort.py` (cron 10 min, par domaine d'expéditeur),
   alors que Wavium embarque un moteur de règles équivalent mais inerte.
9. Le point courrier automatique de 7 h 30 / 18 h 30 est **cassé en cron**
   (`claude: No such file or directory`, rc=127 le 2026-11-23 à 18:30).
10. La stack dev ne sait pas se remettre d'une install interrompue : `make up`
    boucle sur `permission denied for table oc_migrations`, seul `make reset`
    répare.

### Fiche 1 — V4-24 : tags de classement, posables par l'agent

**Catégorie d'origine** : B.
**Symptôme observé** : l'agent `claude-mail` ne classe rien. Son seul droit
d'écriture habituel est l'étoile (`~/.claude/agents/claude-mail.md`, « Mettre une
etoile … C'est ton seul droit d'ecriture habituel »), parce que la couche MCP ne
propose aucune écriture de tag : `mail_message_update` n'accepte que `seen`,
`starred`, `folder` (`server/agent/mail/write.ts:233-237`), le pont PHP n'a pas de
méthode tag (`apps/mail/lib/Controller/AtriumAgentController.php`), et
`server/agent/mail/read.ts` ne renvoie même pas les tags existants.

**Objectif mesurable** : sur une instance de démo, un agent avec `mail: write`
pose et retire les 5 tags `spam`, `promo`, `important`, `urgent`, `etudes` sur un
mail donné ; les tags apparaissent dans l'UI Mail et dans `mail_message_list` ;
un mail corrigé à la main refuse toute modification par l'agent.

**Décisions, preuves à l'appui du code existant**

1. **Multi-tags, sur deux plans.** Le modèle de données sépare déjà une catégorie
   exclusive (`oc_mail_triage.category`, une colonne) de prédicats indépendants
   (`urgency`, `needs_reply`, `needs_action`, `suspicious`). Les 5 tags demandés
   ne sont pas exclusifs entre eux : un mail d'examen est `etudes` **et**
   `urgent`, une promotion frauduleuse est `promo` **et** `spam`. Donc :
   - plan exclusif (la `category` existante, étendue) → `spam`, `promo` (= `ads`
     renommé à l'affichage), `etudes` (nouveau), et les 7 autres déjà présentes ;
   - plan cumulatif, dérivé des prédicats → `important`, `urgent`.
   Les 5 tags visibles sont donc une **dérivation déterministe** de la sortie du
   classifieur, pas un champ libre.
2. **Mail non classable → aucun tag**, `category` reste `NULL`. On n'introduit pas
   de valeur `non-classe` : l'UI sait déjà dire « Not classified »
   (`apps/mail/web/index.tsx:537`), et une valeur sentinelle polluerait les
   filtres (`filterCategories`, `apps/mail/web/api.ts:410`).
3. **Source de vérité : `oc_mail_triage`** (schéma vérifié sur la base dev :
   `account_id`, `msg_hash`, `version`, `model`, `category`,
   `category_confidence`, `urgency`, `urgency_score`, `needs_reply`,
   `needs_action`, `has_deadline`, `written_by_person`, `suspicious`, `raw`,
   `classified_at`). Les tags sont **miroités** dans les tables de tags Mail
   (`oc_mail_tags`, `oc_mail_message_tags`) sous 5 libellés réservés
   `$wavium_spam`, `$wavium_promo`, `$wavium_important`, `$wavium_urgent`,
   `$wavium_etudes`, `is_default_tag = false`, afin qu'un téléphone les voie
   (ce sont des mots-clés IMAP, `apps/mail/web/Tags.tsx:4-6`).
   Le miroir est **à sens unique** (triage → IMAP) et reconstruit à chaque
   classification ou correction. En cas de désynchronisation, `oc_mail_triage`
   gagne. La jointure est propre : `oc_mail_message_tags.imap_message_id` est le
   Message-ID et `oc_mail_triage.msg_hash` en est le md5
   (`TriageService::hash`, ligne 137).
4. **Extension, pas remplacement.** `questions.json` gagne le choix `etudes` ;
   `TriageService::summarize()` (ligne 568) et `publicRow()` (ligne 1068) ne
   changent pas de forme. La dérivation des 5 tags est un module **pur** neuf,
   `server/agent/mail/tags.ts`, côté Bun : c'est là que vivent la couche agent et
   le miroir, et PHP garde l'écriture de la classification telle quelle.
5. **Contrat de classification.** Entrées : celles que `buildInput()` fabrique
   déjà (ligne 597) — en-têtes tels qu'un client les montre puis le corps coupé à
   `triage_body_chars` (6000 par défaut). Sortie par mail :
   `{category, category_confidence, urgency, urgency_score, needs_reply,
   needs_action, has_deadline, suspicious}`. Dérivation :
   - `spam` ⇐ `category == 'spam'` ou `suspicious >= 0.6`
   - `promo` ⇐ `category == 'ads'`
   - `etudes` ⇐ `category == 'etudes'`
   - `urgent` ⇐ `urgency ∈ {today, now}`
   - `important` ⇐ `needs_reply >= 0.6` ou `needs_action >= 0.6` ou
     `has_deadline >= 0.6`
   Seuils : 0.6, **le seuil déjà utilisé par l'UI** pour ses chips
   (`apps/mail/web/index.tsx:499-503`) — on ne crée pas un deuxième seuil.
   `category_confidence < 0.6` → aucun tag de plan exclusif.
   Le prompt interdit déjà au modèle d'obéir au mail (`server/ai/triage.ts:47`) :
   rien à ajouter côté injection.
6. **Outil MCP** : un seul outil d'écriture,
   `mail_message_tag` — `{message_key: string, add?: string[], remove?: string[]}`
   → `{tags: string[]}` ; `area: 'mail'`, `action: 'write'`. Il passe donc
   automatiquement par les modes d'accès existants (`off` / `allowed` /
   `approval`, `server/agent/access.ts:12`) : si le propriétaire a mis
   `write: 'approval'`, l'appel renvoie `{status: 'pending_approval', request_id}`
   sans une ligne de code d'approbation en plus. Côté PHP, une méthode `tag()`
   dans `AtriumAgentController` (IMAP appartient à PHP), refusant tout libellé qui
   n'est pas un tag de l'utilisateur.
   Lecture symétrique : `mail_message_list` et `mail_message_get` renvoient
   `tags: string[]` (voir fiche V4-32).
7. **La correction humaine est un verrou dur, pas un indice.** Aujourd'hui elle
   devient une phrase dans le prompt (`server/ai/triage.ts:109-114`, 20 maximum)
   et le modèle peut encore trancher autrement. On ajoute
   `atrium_mail_tag_locks (uid, account_id, msg_hash, tags, at)` :
   un mail verrouillé est ignoré par la dérivation et `mail_message_tag` y répond
   `conflict`. Le verrou est posé par le `WrongDialog` existant
   (`apps/mail/web/index.tsx:541`) et par lui seul.
8. **Réversibilité.** Un tag ne déplace ni ne supprime jamais un mail. `spam`
   reste une étiquette : déplacer vers Indésirables demeure une action séparée et
   explicite (`mail_message_update`, ou une règle), et `mail_message_delete` ne
   fait toujours que corbeille 30 jours (`server/agent/mail/write.ts:258-262`).
   Règle A-10 respectée.
9. **Évaluation.** Jeu de mails étiquetés à la main dans GreenMail, en réutilisant
   `server/agent/mail/fixture.ts` et les mails de démo de `deploy/dev/init.sh`.
   En CI, avec le provider `mock`, on mesure la **dérivation** et le **miroir**,
   pas la qualité du modèle — le mock ne peut pas mesurer une justesse.
   La justesse par tag (précision / rappel sur ~40 mails étiquetés) se mesure par
   une commande à part, lancée à la main avec un vrai provider, hors CI. À écrire
   dans la fiche, pas à faire passer pour un test.

### Fiche 6 — V4-29 : rendre le moteur de règles utilisable sans IA (et retirer `sort.py`)

**Catégorie d'origine** : B. **Symptôme** : Wavium embarque un moteur de règles
avec UI, proposition en langage naturel, aperçu et exécution
(`server/agent/rules/`, `apps/mail/web/Rules.tsx`), dont les conditions couvrent
exactement ce que fait le script externe : `from_domain` avec correspondance des
sous-domaines (`engine.ts:52-57`). Mais il ne se déclenche que sur les lignes
nouvellement ajoutées à `mail_triage` (`index.ts:192-193`), donc jamais sans IA.
Le classement quotidien réel est donc assuré hors de Wavium par
`/home/oxygen/claude-mail/sort.py` (cron 10 min, 165 lignes).
**Objectif** : les règles à condition purement déterministe (`from`,
`from_domain`, `subject_contains`) se déclenchent **à l'arrivée du mail**, sans
classification ; les 11 règles de `rules.json` sont reproductibles dans l'UI, et
`sort.py` peut être arrêté sans rien perdre.
**Fichiers** : `server/agent/rules/index.ts` (déclencheur), `engine.ts`
(`RuleThen` + exclusions), `server/agent/mail/arrival.ts` (source d'événements
d'arrivée déjà existante), `apps/mail/web/Rules.tsx`.
**Étapes** : 1. séparer les règles « sans IA » des règles à condition
`category` ; 2. brancher les premières sur l'arrivée (`arrival.ts`) et garder les
secondes sur la classification ; 3. ajouter l'action `tag` à `RuleThen`
(`engine.ts:20-24`) ; 4. ajouter une liste d'exclusion par domaine, équivalente au
`never_touch` de `rules.json` (`wanadoo.fr`, `gmail.com`, `umontpellier.fr`…) ;
5. importer `rules.json` une fois.
**Tests** : `server/agent/rules/rules.test.ts` — règle déterministe sur mail non
classé, exclusion qui gagne sur une règle, action `tag`, idempotence
(`atrium_mail_rule_log` a déjà une clé primaire par mail) ; test de non-régression :
un déplacement reste un déplacement, jamais une suppression.
**Risques** : un déclencheur à l'arrivée s'applique à plus de mails qu'avant — la
liste d'exclusion doit exister **avant** le déclencheur, pas après ; A-10 oblige à
ne jamais transformer une règle en suppression. **Effort** : L.
**Dépendances** : l'action `tag` dépend de V4-24.

### Fiche 7 — V4-30 : une correction humaine devient une consigne, pas un indice
